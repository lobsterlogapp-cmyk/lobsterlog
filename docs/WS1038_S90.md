and cross-checked against the on-disk 234 XSD. Headline: the multi-day timestamp work is

The one code value that differs from a WS0000 success is LGRID_ID.

logId LL-20260702-003, subform 90 (MAR), two failed attempts today (2026-07-02 11:37:40 and

All four are valid 12-digit date_12, all on the SAME day, correctly ordered (sail ≤ effort

per-field-date change produced clean, in-order timestamps here.

There are no LAT or LONG elements in the document. FMA_ID is 1589 (LFA 34), which is not MAR

## Success-vs-failure diff — the only delta is LGRID_ID

Compared the failed send against the most recent WS0000 success on the same test licence
(LL-20260701-001, 2026-07-01, also MAR-90, also FMA 1589 / LFA 34). With the naturally
varying values masked (dates, weights, gear counts, trip number, LGBK_UID), the two
documents differ in exactly ONE line:

    - <LGRID_ID>29192</LGRID_ID>   (success — WS0000)
    + <LGRID_ID>29190</LGRID_ID>   (failure — WS1038)

Everything else is identical: same FMA_ID 1589, PORT_ID 21681, BT_TYP_ID 1283, BT_COND_ID
1232, USG_ID 37822, GEAR_ID 925, SPECIE_ID/SPECIE_FRM_ID, structure, and element order.

Both grid codes are listed as valid grids for LFA 34 in our own reftable
(DFO_LGRID_BY_FMA["1589"] in dfoConstants.ts): codeId 29190 → display 67, codeId 29192 →
display 69. So per our local data both are legitimate LFA-34 grids — yet 29190 draws WS1038
and 29192 is accepted.

In the 234 XSD, LGRID_ID is `type="integer_10"` (a plain integer, not an enumeration — the
XSD has only two enumerations and LGRID is not one), so 29190 is XSD-valid, which is why our
xmllint passes it. That means the WS1038 on 29190 is coming from DFO's SERVER-SIDE
validation of the grid value (a live reference-table / permitted-grid check DFO reports
under the WS1038 banner), or from a stricter server XSD than our on-disk copy — not from
anything in the document's structure or the timestamps.

Plainly: grid 67 (codeId 29190) is being rejected by DFO for this licence/FMA while grid 69
(codeId 29192) is accepted. This is a grid-code data issue, not the multi-day timestamp
work. Likely explanations to run down (your call, not fixed here): our MV_GRID/LGRID
snapshot for LFA 34 includes a grid DFO's live table no longer accepts (reference-data
drift), or grid 67 is not a permitted grid for this test licence in UAT. A quick
confirmation: re-send LL-20260702-003 with LGRID 29192 (known-good) unchanged otherwise — if
it returns WS0000, the grid value is confirmed as the sole trigger.

## Coordinate emission — raw vs clamped (234 vs 222)

dfoXmlGenerator.ts (234 logbook), lines 283–289:

    // LAT/LONG: Rule 3059 — MAR(90) FMA 38b only …
    if (subformId === 90 && Number(d.fmaId) === DFO_FMA_38B && d.gpsLat && d.gpsLng) {
      const coordMode = d.gpsSrc === 'gps' ? 'G' : 'M';
      effort += `          <LAT MODE="${coordMode}">${xmlEscape(d.gpsLat)}</LAT>\n`;
      effort += `          <LONG MODE="${coordMode}">${xmlEscape(d.gpsLng)}</LONG>\n`;
    }

State plainly: the 234 path emits LAT/LONG RAW — `xmlEscape(d.gpsLat)` / `xmlEscape(d.gpsLng)`
with no rounding or decimal clamp. The 222/233 path does clamp: dfoForm222Generator.ts
defines `clampCoord4(v)` (line 123, rounds to ≤4 decimals with no trailing-zero pad) and
applies it at emit (lines 155–156: `clampCoord4(entry.lat)` / `clampCoord4(entry.lon)`).

So there IS a divergence: the 234 logbook emits coordinates unclamped, the 222 form clamps
to the XSD's ≤4-decimal limit. This is a latent gap (a hand-typed or high-precision GPS
coordinate in a MAR FMA-38b logbook could hit the same WS1038 the 222 path already guards
against), but it is NOT the cause of THIS failure — no coordinate was emitted for FMA 1589.
Flagging it for a separate decision; not fixing it here.

# WS1038 debug — step 4 (Session 90): re-sent the 07-01 XML — PROVEN DFO server-side

Per request, re-transmitted the byte-exact 07-01 XML (the content that earned WS0000 /
CONF 163045) to the DFO UAT endpoint today (2026-07-02) and read the live response. Two
sends were needed because the first hit a filename guard.

## WS error codes (from ELOG_Web_Service_3_6_Eng.pdf)

- WS0000 — File successfully transferred (success).
- WS1034 — The same file name has already been received by DFO (duplicate FILENAME).
- WS1038 — XML content is not valid against XSD.

## Send 1 — byte-exact envelope (same filename) → WS1034

Re-POSTed the exact stored soapSnapshot from LL-20260701-001 (filename
1004-104460-20260701164548.XML, p_body + p_elogkey untouched) to
`https://inter-w01-uat.dfo-mpo.gc.ca/ws/ElogXMLFileTransfer/ElogXMLFileTransfer.asmx`
with SOAPAction `http://www.dfo-mpo.gc.ca/SaveIncomingFile`.

Response: HTTP 200, `<CONF>163054</CONF><ERR>WS1034</ERR>`.

WS1034 = duplicate filename. DFO checks the filename BEFORE XSD-validating the body, so it
short-circuited on the reused 07-01 filename and never re-validated the content. Inconclusive
for "does the 07-01 content still pass XSD" — so a second send was required.

## Send 2 — same body, FRESH filename → WS1038  (the clincher)

Rebuilt the envelope with a brand-new unique filename (1004-104460-20260702151838.XML) and
the p_body byte-identical to the 07-01 success (verified equal before sending); p_elogkey
unchanged. This bypasses the duplicate-filename guard so DFO proceeds to XSD validation.

Response: HTTP 200, `<CONF>163055</CONF><ERR>WS1038</ERR>`.

So the EXACT SAME XML CONTENT that DFO accepted with WS0000 on 2026-07-01 is now rejected
with WS1038 on 2026-07-02. Nothing in the document changed — same bytes, only the filename
timestamp differs, and WS1038 is evaluated on the XML body, not the filename.

## Conclusion — the app is fully exonerated; DFO changed server-side

This is definitive, not inferential: a byte-identical logbook flips from WS0000 (07-01) to
WS1038 (07-02) with no change to the document. Therefore DFO changed its 234 XSD / content
validation on the server between 07-01 and 07-02. Ruled out conclusively:

- The S90 per-field-date (multi-day) work — the failing sends are same-day and, more to the
  point, this proof uses a pre-S90 document unchanged.
- The LGRID value — a grid accepted on 06-29 (29253) failed on 07-02, and now even a
  fully-accepted 07-01 document fails.
- Any document structure/type issue — the document validates against our on-disk XSD
  (39673.234.…20260130) and is one DFO itself accepted a day earlier.

Corroborating: a Form 233 sent 07-02 10:32 returned WS0000 (CONF 163047) — the endpoint,
auth, and ELOG key all work; only the 234 logbook document is now rejected. That fits a
234-specific XSD update on the DFO side.
